# VideoFlow 4.0 方向 A 可行性验证

问题是能否补回遗漏的受影响镜头，同时少重生成无关镜头。评估使用已有依赖探测用例，代码接在独立研究分支，入口为 `research/dependency_probe/egdr.py`。真实渲染和发布仍由原运行时处理。

## 实验怎么跑

在仓库根目录运行。输出应为新文件。

```sh
python research/dependency_probe/egdr.py \
  --cases research/dependency_probe/visibility_v3_observed.json \
  --budget 1 --output egdr-visibility-v3-cpu.json
```

已有 Ollama 文本模型的机器可加 `--ollama http://127.0.0.1:11434 --model qwen2.5:14b`，使用同一模型比较 Direct、Checklist 和 EGDR，文本输入与加入帧观测记录的输入分别评分。执行前可用 `ollama list` 检查模型。此模式读取帧观测文字，本轮没有运行模型端点或分析原始像素。

## 方法和消融

1. 分离镜头元数据和已有帧观测记录。按目标词是否匹配排列候选，所有非已声明镜头均进入验证，低排名本身不能触发复用。
2. 文本模型模式逐镜头检查实体身份、被编辑属性可见性、作用范围。缺失或无法在输入中定位的引用按未知处理。逐字匹配只核对证据出处，语义仍可能判断错误。
3. 确认受影响的镜头作为新失效种子，原声明和匹配的硬依赖均由 DAIR 求闭包。严格模式重新生成所有仍未知的镜头。探索模式 `--budget 1` 允许每个案例复用至多一个未判明镜头，等价于给每个未知赋单位分数。这个分数不是概率，也不能限制真实漏判率。

默认 CPU 验证器只识别字面否定和宽泛的可见颜色编辑，遇到部件、动作或范围约束通常保留未知。归档案例多数没有真实的硬边标注，硬边传播另由测试覆盖。历史案例作为诊断集，不能充当独立评估。

普通颜色案例中，文本字面匹配已经达到现有标签，复杂验证没有收益。可见性 v3 的观测文字减少 4 个额外镜头，保守 EGDR 却接近全量。将未判明预算放宽到 1 后，保守模式此前没有遗漏的 v3 出现一次漏选。困难案例仍需辨认部件与动作，例如前扣、正在下落的水和位于窑内的碗。

## 进入真实视频实验的条件

冻结新故事的任务、删除的软依赖和双人标注，再从编辑前视频提取帧。帧描述生成阶段不看编辑指令和标签，避免描述为答案定制。按故事划分调参与测试，在同一证据与同一模型上比较字面检索、Direct、Checklist、EGDR，报告逐故事漏选、额外镜头和估计成本，并单列候选排序与验证调用开销。只在新故事上出现更好的漏选与成本权衡后才进入 H3 端到端评估。现有结果只支持继续验证证据来源与分项判断。

## Checklist 漏选复核

`--checklist-recall` 保留原 Checklist 的选择，只复核闭包之外的镜头。对象实例、具体部件或动作、可见性、编辑范围四项均有本镜头文字引文且判为正向时，才新增失效种子。随后沿已有硬依赖传播。输出分别记录复核新增镜头、由依赖传播新增的镜头、逐项证据、原始回复和额外模型调用数。同一次运行也输出 Direct 与 Checklist 的并集，作为直接复用两者结果的简单对照。

先用自行车与咖啡车的四条旧编辑诊断 B1-S1 漏选。这四条曾用于定位问题，应视为开发数据。后续评测使用新故事的编辑前视频，先独立记录帧观察，再冻结编辑、保留的依赖、受影响镜头标注及方法版本。至少包括跨镜头同实体、同类不同实例、不可见部件和零受影响镜头的编辑，并报告每个故事的错误与调用数。比较纯文本与加入帧观察笔记两个输入条件。主要检验是复核相对于 Checklist 是否减少漏选、相对于 Direct 与 Checklist 并集是否在相同漏选数下减少多选，并单独报告能否在零漏选时减少全量重生成。镜头数是代理成本，帧观察笔记是文字证据，模型调用数应独立汇报。
